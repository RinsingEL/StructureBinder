## 本轮确定的职责

| 参与方 | 负责内容 |
| --- | --- |
| 整合包作者 | 实际物品池、基础概率，基础/稀有/史诗等内容档位，以及 Mod 玩法与玩家兴趣说明 |
| AI | 按城市功能选择一个或多个池，决定城市对池及内容档位的修正权重；不逐个配置普通 NPC 或货单 |
| 程序 | 执行权重计算、具体商人/居民物品抽取与刷新，并处理对应交易、赠送场景 |
| 主模组 | 提供可注册的附属规划步骤，衔接 AI 所需任务和工具 |
| 附属模组 | 实现居民、物品规则及相应游戏行为 |

“AI 只选择池、完全不能调整概率”的先前简化表述，以本轮确认为准：**AI 可以调整城市修正权重，作者的基础池仍为配置来源**。不把“调权”扩大成临时创造物品、改写配方或执行脚本。

## 建议的权重语义

采用权重抽选时，可分为两个层级，避免较大的物品池仅因条目多就吞掉其他池的机会：

1. 池选择权重 = 作者基础池权重 × 国度倾向 × 城市功能修正。
2. 池内物品权重 = 作者基础物品权重 × 城市对该档位的修正。

每层在可用候选中归一化：某候选概率 = 它的最终权重 / 同层全部候选权重之和。公式是实现建议，实际配置字段、继承层级及各因子的必要性尚未冻结。作者已有池若采用独立掉落判定，而非互斥权重抽选，需明确对应模式，不能直接把两者混用。

| 示例城市 | 机械池修正 | 农业池修正 | 史诗档修正 |
| --- | ---: | ---: | ---: |
| 以机械制造为核心的国度首都 | ×2 | ×0.8 | ×1.8 |
| 该国农业村庄 | ×0.5 | ×3 | ×0.3 |
| 专门制造精密零件的小镇 | ×3 | ×0.5 | ×2 |

以上仅解释混搭和职能覆盖规模倾向，**不是固定城市模板或默认数值**。相同风格允许不同组合，不同风格允许相同组合。

权重乘二不意味着最终概率严格翻倍；全部候选同时乘同一个系数，归一化后分布不变。权重决定“抽到什么”，货架容量、库存和补货量决定“有多少”，二者应分开表达。具体数量规则还未确定。

## 商品池给 AI 的资料

建议向 AI 提供简短的池目录：池的名称/引用、来源 Mod 或内容、对应玩法、适合的玩家、功能用途与档位说明。实际池条目由作者配置，AI 按需查询，不默认把整包物品清单塞进城市设计上下文。

池可以按 Mod 配置，也可以按用途拆分或跨 Mod 组合；这些是作者组织内容的自由，不强制一种唯一目录结构。“适合的玩家”和“用途”用于帮助 AI 选择，不转变成风格与 Mod 的强制映射。

城市先选择池与权重，程序再把规则应用到商人/居民类型。是否同城商人共享库存、不同商人如何分摊池、不同用途是否引用同一池版本，留待实现前细化。

## 主流程接入建议

建议链路：

```text
城市设计产生可用的功能与设定
    → 主流程发现已注册的附属设计任务
    → AI 获取作者的池目录及城市摘要
    → AI 选择多个池并配置城市权重
    → 附属模组校验、预览、发布规则
    → 主流程继续后续任务

实际住宅和岗位被接入
    → 程序生成人物
    → 程序按已发布池规则生成/刷新物品
```

第一版建议由随游戏加载的附属 Mod，通过主模组公开 Java 接口注册步骤；接入统一规划会话，让内置 AI 与外接 MCP 领取同一种任务。两边在同一游戏进程内可调用共同的业务服务，不必为了衔接而要求两个本地 MCP 服务器互相发 HTTP 请求。已有附属 MCP 可继续作为独立设计入口；接入方式尚未成为正式接口。

注册步骤需要承载：身份与版本、挂接位置与依赖、城市上下文、任务资料及工具定义、动作处理和完成判定。主流程需要保存每个步骤的进度与结果，支持恢复和重试；不能仅凭 AI 自称完成就推进，也不能把一次重试当作再次生成全部人物或商品的依据。上述为待实施技术建议，正式字段另写契约。

第一版倾向固定挂接点与有序附加步骤。具体是在城市蓝图定稿后还是编译可用后运行，需与当前城市队列核对；附属规则可先发布，实际人物等待住宅被发现后生成，避免设计队列必须等玩家探索完整城市。

## 预期重构范围

按本轮只读核对，主模组已有统一规划会话可复用，需要改造的主要位置是阶段发现与分派、工具定义与执行注册、回合完成判定、城市队列的附属任务状态及完成条件。

相关实现入口：

- `ProviderPlanningDiscovery`、`PlanningStepPolicy`：目前按内置阶段判断任务及可用工具。
- `PreparedPlanningTurn`、`PlanningSessionService`：内外 AI 共用的任务准备和会话入口。
- `ProviderPlanningToolCatalog`、`ProviderPlanningToolGateway`、`PlanningTurnControl`：工具定义、执行范围和完成判断。
- `CityDesignQueue`：当前城市推进与等待生成状态。

源码位于 `E:\Mod_Dev\StructureBinder\src\main\java\com\rinsing\geomantia`。重构重点是流程调度与能力注册，不以重新实现城市布局或地形算法为前提。

附属模组需要新增池配置、城市池绑定与权重、货架库存、赠礼请求与判定状态，以及独立多格商店交互。当前 v0.3.0 是每个职业最多 12 条固定交易、绿宝石结算、对话按钮展示；没有通用池刷新、库存、独立多格货架或请求赠礼的掷骰交互。两边目前也没有自动串联居民设计。

## 统一货币与收购循环的确认补充

用户已确认喜欢“出售生产或探索所得，再采购所需材料”的循环，并要求统一货币。交易系统因此需要同时支持出售商品与收购玩家产出；作者配置可收购的内容与基础规则，城市功能决定供应和需求的特色。

价格分工方向已获接受：作者提供基准价格与允许档位，AI 选择城市档位，程序计算并执行。尚未确定的是具体价格表、倍率、收购预算及供货规模，不再把“是否允许 AI 选择价格档位”列为未确认方向。

为降低使用门槛，建议提供可调整的默认经济配置，先通过挖矿、种菜、出售与采购建材的实际循环检查购买力，再调整数值。用户不需要先逐件手算价格。

货币表现形式仍是提案：倾向统一账户余额，在商店直接显示余额并支持批量买卖；是否采用实体钱币、货币名称、是否覆盖委托奖励/购地和如何兼容其他 Mod 的货币，尚未逐项确认，不在本次产品需求中写成固定实现。

## 主动请求商品赠礼的讨论补充

用户提出：赠礼看 NPC 对玩家的好感度，玩家可以主动请求，随后掷骰判定；赠品直接取自现有商品，并考虑把好感度与稀有度结合修正成功概率。该方向替代先前独立抽取赠品的建议。借鉴掷骰交互不代表照搬某款游戏的具体骰型、属性或特殊点数规则。

建议交互为：在商店选中商品及请求数量，选择请求赠送，查看关系带来的帮助与请求难度，掷骰后由 NPC 同意或婉拒。成功时转移所请求的实际库存，购买与赠礼消耗同一批货，不能复制出一份额外商品；此库存处理为待确认的实现建议。

概率设计建议如下，尚未冻结公式和默认数值：

- 稀有度采用作者配置的内容档位，决定基础赠送难度或基础成功率；好感度采用 NPC 与当前玩家的关系，提供正向修正。高好感更容易成功，高稀有度更难成功，不能直接把“越稀有越大的系数”当成成功率加成。
- 如采用乘算，把好感映射为非负修正系数，并约束最终成功率范围；不直接把原始好感数值或商品抽取权重当作概率。已有商品的出现概率不因玩家发起赠礼请求而重算。
- 请求数量与总价值建议参与难度或赠礼额度判断，避免请求一个普通物品与请求整组普通物品完全等价。与商品价格的具体关系待定。
- 掷骰是一次真实判定的展示。采用何种骰型与概率映射继续讨论，界面所展示的成功条件应与实际判定一致，不在后台与界面分别随机两次。

为保留关系价值并避免反复点击直到成功，建议按 NPC 设置请求间隔和一段时间内的赠礼额度；换商品、重新打开商店不能重置次数。失败默认只是婉拒，不因一次正常请求直接扣好感；关系恶化、过度索取等额外后果尚未确认。

普通居民也允许被请求赠礼，已获用户接受；其物品由配置及程序生成，并从实际持有的物品中赠送。请求次数是否按玩家单独计算、赠礼额度是否由所有玩家共享、刷新规则、不可赠送物品和普通居民可展示的请求范围，均留待后续细化。具体数量、成功率、失败处理与限制目前都是建议，不自动加入已确认产品要求。

## 职业与能力的当前边界

本轮只读核对：当前 `Design.Profession` 已是可配置模板，包含名称、能力集合、工作用途、作息、装备等；`Design.Patch` 支持新增职业，城市通过 `jobs` 引用职业模板并设置构成。`Dialogues` 和 `SocietyRuntime` 按能力决定交互及行为。职业 ID 不限制为初版七个名称；默认模板、旧配置迁移与外观映射仍保留原有名称。

当前程序提供固定的已实现能力集合，并验证组合限制；AI 可以组合这些能力，新增真正的行为需要先开发。职业模板目前为世界级目录，城市分别引用；同名但能力或内容不同的城市职业可使用不同 ID。模板总量仍有原型上限，按大量城市扩展时需要复核容量，不能把现有模板目录描述为无限。

新经济能力沿用这一职责分工：作者提供可用物品池，AI 配置城市职业模板的能力与池组合，程序批量生成居民及实际物品。建议让交易、收购与接受赠礼请求分别可配置，并允许普通居民只参与赠礼；不能依据职业名称硬编码物品和行为。具体能力名称、字段及组合限制尚未发布，当前代码的 `offers` 仍是固定交易清单，新池和赠礼尚未接入。
