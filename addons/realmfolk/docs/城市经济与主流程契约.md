# 城市经济与主流程契约 · 0.4.0

需求依据：[城市物品池与多商品交易](E:/Mod_Dev/designer_territoryMod/docs/addons/realmfolk/需求案/05_城市物品池与多商品交易.md)。本文件描述可执行配置和存档语义；此前设计草案保留为讨论记录。

## 作者配置与 AI 权限

`config/realmfolk/economy.json` 是整合包作者的经济目录，首次启动从 `realmfolk/economy-default.json` 创建，随后仅在服务器启动时读取。物品必须属于当前已安装 Mod；不存在的物品、未知引用或无效数值会报出配置路径并拒绝启动经济服务。不会把缺失的 Mod 物品换成别的物品。

| 字段 | 含义 |
| --- | --- |
| `currency` | 账户货币显示名称，默认通币；所有城市共用玩家账户 |
| `goods` | 以注册物品 ID 为键；`tier` 档位、`price` 每件出售基价、`buyback` 每件收购基价（0 不收购）、`gift` 能否赠送 |
| `tiers` | 作者定义档位 ID、显示名和赠礼基础成功率 `giftChance`（百分数） |
| `pools` | 池名称、`interests` 玩家兴趣、`function` 功能说明、池基础 `weight`，以及 `entries` |
| `entries` | `item` 引用 goods；基础 `weight`；库存数量 `min/max`；`guaranteed` 是否常备 |
| `priceBands` | 作者允许的档位，`sell/buy` 为出售/收购价格倍率，范围 0.25–4 |
| `defaults` | 未单独设计城市的多池选择、档位权重与价格档位 |
| `restockTicks` | 补货间隔，默认 24000 游戏 tick（正常速度 20 分钟） |
| `requestCooldownTicks` | 同一玩家向同一 NPC 的请求间隔，默认 12000 tick；失败也计入 |
| `buybackBudget/giftBudget` | 每位 NPC 每期共享的收购/赠礼额度；默认 4096/48 通币 |
| `affectionFactor` | 好感乘算系数，默认 0.025 |
| `legacyUnit` | 旧委托、购地、罚款与固定奖励的数值换算，默认每旧单位 16 通币 |

默认目录包含建造、农业、矿材、探索四个示例池，只有原版物品。加入机械动力、农夫乐事或魔法 Mod 后，由作者把真实注册 ID 加入 goods 和任意多个池，并补上兴趣与功能说明；没有风格到 Mod 的程序映射。

AI 的城市方案增加 `economy`：

```json
{
  "pools": {"building": 1.5, "farming": 2, "mining": 0.7},
  "tiers": {"basic": 1, "rare": 0.8, "epic": 0.2},
  "priceBand": "producer"
}
```

池和档位引用必须存在，倍率范围 0–10；至少有一个有效候选。省略某个档位倍率表示 1。省略整个城市 economy 使用作者 defaults。AI 可混选多池，不可通过 MCP 改写作者目录或每件基价。

职业继续是数据模板：`trade` 出售，`buyback` 收购，`gift` 接受赠礼请求，三项可以独立组合。`itemPools` 为空时使用城市选中的全部池；非空时取与城市已选池的交集。`stockSlots` 控制物品种类数，范围 1–54，界面分页。职业名称不决定能力或物品。

## 抽取、库存与成交

先放入已启用池里的常备品，再填充剩余格子：先按“作者池权重 × 城市池倍率”选择池，再按“作者物品权重 × 城市档位倍率”选择物品。池大小不会直接放大该池概率。多池引用同一物品合并为一格，随后从各池候选中移除；常备品多于货架容量时按物品 ID 排序截取，因此作者应为常备货预留格数。

同一个物品的基础价格和档位由 goods 统一定义。成交出售单价向上取整，收购单价向下取整，且收购单价最多为同城出售单价减 1；城市之间允许不同档位差价。收购目录来自该 NPC 已启用的池，不依赖本次随机货架是否抽到该物品。售给城市的产出计入城市消耗，不另复制进商人货架。

库存、单价快照、额度、下次补货时间、请求间隔和最后骰子结果保存在 NPC 存档中。购买与赠礼扣除同一库存；打开、关闭界面或重进世界都不补货。经过补货间隔后，下次访问才生成新一批库存，旧货不会累加。规则更新在下次补货生效，避免正在交易时重抽。

每次打开/成交后的服务端报价有独立凭据，并携带库存版本；客户端只能提交动作、索引和数量。服务端验证距离、视线、能力、余额、物品、数量、库存和版本；重复网络请求不能重复成交，其他玩家改变库存后旧报价失效。背包放不下时不扣款；不静默丢弃物品。出售会合并背包里的同类普通物品，带附魔、改名、损耗等额外数据的物品不列入普通收购。

## 赠礼

选中实际持有的物品与数量后，可以主动请求。基础概率取自物品档位，乘以 `max(0, 1 + 好感 × affectionFactor)`，再除以请求数量的平方根，向下取整并限制在 0–95%。总价值不得超过对方剩余额度；不可赠送物品和零成功率请求不可发起。

服务端只掷一次 d100，点数小于等于界面成功条件即成功；界面动画展示这次真实结果。成功扣实际库存和 NPC 共享赠礼额度，失败不扣库存、不降低好感。请求间隔按玩家与 NPC 分别保存，换商品和补货不会清除尚未到期的间隔，额度则由所有玩家共享。

默认数值用于试玩，作者可以统一调整；它们不是冻结的平衡标准。

## 主模组城市流程

已针对主模组提交 `791e5b71` 编译与联调。只依赖主包的 `com.rinsing.geomantia.api.planning`，不引用可选 Harness 或地图包。

`realmfolk:city_society` 注册到 `AFTER_CITY_PLANNING`。扩展版本包含作者经济目录的摘要；重启后目录变化会使相应任务需要重新设计。主 MCP 或 Harness 提供同一组工具：

1. `realmfolk_planning_context`：城市/国度设定、现行方案、能力、池目录、价格档位与草案。
2. `realmfolk_planning_read`：按需读取职业或池。
3. `realmfolk_planning_submit`：`baseRevision`、完整 `plan`、可选局部 `professions`。
4. `realmfolk_planning_preview`：返回人口统计、保护人数与发布凭证。
5. `realmfolk_planning_publish`：发布并原子持久化后，主流程才能记录完成。

主 MCP 的 `planning_action` 返回多个文本块：首块是宿主状态，后续块包含 `extensionOutput.result`，提交草案的 draftId 和预览凭证在后者。

城市方案按 `runId:citySeedId` 隔离。每城可提交最多 16 种局部职业，程序自动添加城市命名空间；不同城市可以使用同一职业称谓而能力不同，不能引用别城私有职业。世界职业目录最多 4096 项，城市方案最多 512 个。

没有加载城市时，预览 created=0 可以正常发布；真正发现住宅与岗位后才生成居民。主流程发布采用 `future_only`，保留所有已有 NPC 的 UUID、房屋、关系和快照。人工需要刷新未受保护人物时，仍可用独立 Realmfolk MCP 的显式范围事务。

同一任务重复发布可恢复，不重复造人。任务、城市或蓝图版本不符的草案拒绝发布；主流程草案不能绕过作用域由独立 MCP 发布。草案、世界修订和发布回执保存于 `realmfolk_society.dat`，主模组同时保存其流程回执。

## 城市功能填写表（2026-09-27）

用户确认以程序生成的功能事实表驱动 AI 分批配置。主流程扩展协议标识升级为 `0.5.0-worksheet-*`，使旧任务回执不能直接充当新题单完成证据。模组包版本仍为 0.4.0。

程序读取 D4 `structure_anchor_plan.json` 中实际编译保留的 anchors，并关联冻结目录中 approved 的 `functionTerms`；每种功能给出建筑数、功能区 ID 和模板 ID。未选中的候选模板不计数；没有批准语义的锚点单独列出。一个多用途建筑可以出现在多个功能行，住房汇总按 anchorId 只算一次。

每行填写 `functionTerm / housing / professions / reason`，保存于 `plan.functionAnswers`。`housing` 必须与 `overrides.housingTerms` 一致；`professions` 引用共用职业定义，必须命中对应工作用途（无固定工作地的职业只能关联住房功能）。无人功能填写空职业列表并说明理由。每个配额职业至少关联一行。

全城填写人口模式、住房用途、每屋人数/入住率或固定目标、售房预留、岗位容量、活动（允许明确空列表）、关键人物（允许空列表）和经济选择。`residentsByFunction` 可按住房用途覆盖人数（1–8）；多用途匹配多个值取最大值，不累加。未匹配时沿用明确的 `residentsPerHouse`。运行时仍受实际站立点数量限制。

新职业显式填写能力、工作地点、休息时段；启用 `commission` 必须完整填写 `item/count/emeralds/affection/reputation` 和 `commissionPurpose`，后者说明职业关联，不产生额外任务逻辑。具有 trade/buyback/gift 时显式填写 itemPools、stockSlots、goodsPurpose。复用现有职业先读取完整定义，在提交根对象 `reuseProfessions` 中显式确认；新定义与复用不能同时填写同一个 ID。

新增工具：

| 工具 | 输入与行为 |
| --- | --- |
| `realmfolk_worksheet_read` | `section=summary/functions/professions`，offset 从 0 起，limit 为 1–8。返回填写版本、进度、分页事实及已填值。summary 返回全城配置，不回传完整职业表。 |
| `realmfolk_worksheet_update` | baseRevision、worksheetRevision、patch。每次保存差异并持久化；functionAnswers 按功能替换行，professions 按职业 ID 完整替换定义，其余对象逐键合并、数组整体替换。removeJobs/removeProfessions 显式删除。允许保存未完成答案，拒绝结构错误和过期版本。 |
| `realmfolk_worksheet_submit` | worksheetRevision。校验完整保存表，缺项返回 `status=incomplete` 和具体 errors；成功返回 draftId 与 cityReview。 |
| `realmfolk_worksheet_reset` | worksheetRevision。显式清空该城未提交填写，不修改已发布规则。世界版本改变后需重审；任务版本改变后重新生成题单。 |

原完整 `realmfolk_planning_submit` 仍可使用，执行相同表格校验。两条路径均走现有 draft → preview → publish；新 publish 必须携带预览返回的 `reviewToken` 和原 `previewToken`。回执可重放并受城市/任务隔离。AI 先审查全城报告再发布，服务端可验证凭证，不能证明模型实际阅读了文字。

报告含功能覆盖、去重建筑/住房数、站立验证和售房扣除前的规划人口上限、职业配额、完整职业配置、有效商品池、保底商品数、剩余随机槽位、完全相同委托警告。商品保底挤占仅报告警告，本次不改变作者已有抽取规则。加载后真实住房/人口统计仍来自原 preview.towns；towns 为空不能当作实际人口验证通过。

填写表和审查凭证与社会数据一起保存。旧存档缺新字段时默认空表，不删除已有 NPC。主流程发布保持 future_only，本轮不自动刷新已有 NPC 快照。

## 旧存档与独立 MCP

原版本 2 社会存档保持可读。首次经济升级只给已有会话型居民加入 gift，给原 trade 模板加入 buyback，保留身份、住房和关系。原 `offers` 字段保留读取兼容，但新货架以作者经济池为准，不再直接执行绿宝石按钮交易。原绿宝石物品仍在背包里，可按作者目录作为普通商品出售；不会自动拿走玩家物品。

委托、护送、购地、讨伐奖励及罚款统一使用同一账户。旧字段（例如 commission.emeralds、housePrice、法定 fine）按 legacyUnit 转换，保留旧世界数值规模。`/realmfolk journal` 和对话都显示余额。

独立 MCP 新增 `realmfolk_economy_catalogue`、`realmfolk_read_pool` 两个只读工具，原设计草案工具继续使用同一个校验与发布服务。经济池源文件由作者离线编辑，重启生效；不能通过 AI 工具生成脚本或修改基础价格。
