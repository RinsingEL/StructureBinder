# D4 城市设计流程

## 设计目标

把本城要求落实为适应现场地形、功能完整、具有整体性且体量相称的城市。每次进入世界都应能探索一座有文明生活的异世界城市；依据这次地形和作者素材作出具体设计。

设计与终审始终检查四件事：

1. **满足城市要求**：citySeed 的定位、coreFunctions、gameplayRequirements 与服务地位，落实到实际建筑、配套和公共空间。说明这些空间服务谁、发生什么活动。
2. **地形与功能相互关联**：入口、中心、安静区域、生产和生活等安排利用真实地貌与群系；说明为何放在那里、如何与其他空间联系。
3. **全城成为整体**：先有一个能一眼读懂的空间骨架，再有各区。整体性比数量优先：一座紧凑、主次分明的城胜过铺满场地的分散建筑。
4. **体量与职责相称**：按城市职责和现场容量决定体量，不设建筑或阵列数量指标。扩展必须贴着已有骨架长出；在远处另开孤立组团不算扩展，而是削弱整体。

## 空间构图手法

以下是让城市"成为整体、有层次"的具体做法，按顺序使用。

### 1. 先定骨架：一条主轴、一个中心

- 在 D3 地图上找出入口（岸边、道路来向或低处）和制高点或最好的平地。连接两者的方向就是**主轴**，城市最重要的序列沿它展开：入口 → 前导空间 → 中心广场 → 核心建筑。
- 全城只用**一个或极少数根组合**，用 anchorBlock 定位；其他组通过 arrayCompositions 嵌套在它下面。根锚点越多，城市越容易碎成互不相干的岛。确需第二个根时，它应紧贴主骨架（与已有组团净距通常不超过 30 格），而不是放在场地另一端。
- 中心广场或主庭院放在主轴与次轴的交点。主要的二、三级建筑放在广场四边或轴线端点，形成"在广场上能看到全城重要建筑"的关系。

### 2. 建筑分级：一个地标，少数次级地标，其余成组

- **一级地标**：全城最大、最高、功能最重要的那座（例如礼堂、宫殿、主神殿）。放在主轴尽端或制高点，正面朝向主轴或广场。全城只有一个。
- **二级地标**：2～4 座有独立功能的大建筑（书馆、观测台、议事厅、食堂）。放在广场边、轴线另一端或次轴端点，与一级地标保持可见关系。
- **普通建筑**：同类小建筑（课堂、宿舍、商铺、作坊）放进**同一个**阵列，组成街坊或围院。不要把同类建筑拆成许多 1～2 栋的小组，那只会产生碎片。

### 3. 公共空间是"图形"，不是剩余空地

- 先定庭院和广场的尺寸，再让建筑围合它。用 COURTYARD 阵列并开启 `faceInward`，让围合建筑正面朝向公共空间。不开 `faceInward` 的庭院，四周的楼会背对庭院。
- 尺度要和围合它的建筑相称：庭院边长约为围合建筑宽度的 1～1.5 倍，主广场约 50～80 格。超过周边建筑体量很多的空旷广场会显得空洞，过小又会被建筑压住。
- 同一条主轴上，空间应有收放：前导空间较窄，中心广场开阔，核心庭院较安静。庭院、广场、花园各有服务对象和入口。
- 绿化也要有结构。用 public_realm 的 `spaces` 为主要公共空间设计构图：主轴和主路两侧用 PATH_EDGE 种植区或 LINE 布置行道树；广场中心或轴线交点放一个 POINT 焦点（泉、标景、孤植大树）；庭院用 RING 或 GRID 对称布置。`greenery` 与 `fringe` 的随机撒点只作为底色，不能替代这些有意图的布置。`spaces` 为空时，全城绿化会是均匀散点，没有章法。

### 4. 疏密梯度：中心疏朗，生活紧密，外围舒展

- 不同组团用不同的 `gapBlocks` 与 `densityClass`。参考值：地标与主庭院 8～12，宿舍、商铺、作坊街坊 4～6（DENSE），农田与苗圃用 CONTIGUOUS 紧贴成片，放在外围。
- 所有组都用同一个 gap、同一个密度，是"看起来均匀撒开、没有层次"的主要原因。

### 5. 地形承担层级

- 一级地标占高点或主轴尽端；台地按重要性分级，核心区台地最高，广场与生活区逐级降低。相邻台地的高差形成拾级而上的序列，而不是各区各自孤立的平台。
- 岸边、低地给入口、码头和农林；陡坡、水湾和林带作为全城边界或区间的自然分隔，并说明它们在构图中的作用。

### 6. 阵列拆分规则

只有空间用途不同时才拆分阵列（例如"围合主庭院的楼"和"宿舍街坊"）。同一用途的重复建筑放进同一个阵列，用 count 与 fillPools 控制数量。子阵列应通过嵌套组合到父组团里，而不是各自用 anchorBlock 漂在地图上。

## 按人定区：先定岗位，再定住处与公共空间

城市热不热闹，取决于每个时段每类区域里有没有人，而不只取决于总人口。功能区按人在一天中去哪里分成三大类，在功能区 role 开头写明：

| 大类 | 什么时候人多 | 规模怎么定 |
| --- | --- | --- |
| 【工作】 | 白天 | 由城市职责决定岗位，最先定 |
| 【居住】 | 夜里、累了 | 由全城人口倒推床位 |
| 【公共】 | 饭点、傍晚、节日 | 由全城人口推算座位与停留空间 |

按以下顺序估算，并把结果写进各区的 population：

1. **工作区定岗位和服务对象。** 每个工作区写清需要哪些职业、各多少人（jobs），以及服务多少不上班的人，例如教学区有 60 个学生座位（写在 purpose）。据此决定盖几栋，不要按“场地还空”加楼。templateFacilityCapacities 的 workplaces 是模板里的工位总数，不等于在岗人数：居民模组对每栋的在岗人数另有上限，按两者中较小的一个估算；上下文没有给出上限时，按每栋约 4 人估算并在说明里注明。
2. **算全城人口。** 人口 = 各工作区岗位之和 + 不上班的人（学生、家属等）。商店、食堂既是店员的工作区，也是顾客的公共区；岗位计入工作，顾客计入公共容量，不重复计人。
3. **居住区按人口定床位。** 床位约为人口除以入住率（约 0.85）。按 templateFacilityCapacities 的床位数决定宿舍栋数，写入居住区的 residents 与 housingGroupIds。住处尽量靠近工作地，例如教职宿舍贴近教学区。
4. **公共区按人口定容量。** 食堂座位约为人口的三分之一（分批用餐），主广场能容纳全城人口的一部分同时停留。容量和服务对象写在公共区的 purpose。
5. **公共区放在通勤路上。** 宿舍到工作区之间经过广场、食堂和集市，居民每天往返时自然从这里穿过。

只统计一次：工作区只填 jobs、residents 为 0；居住区填 residents 与 housingGroupIds，jobs 只填在宿舍里值班的岗位。学生和普通居民可以没有固定工作点。

## 对照示范：魔法学院的骨架

下面是工作台中一座"看起来是整体"的魔法学院的组织方式，仅示范手法；具体坐标、素材和规模以本次地形和目录为准。

```text
海湾码头（东南岸）─┐
                   ▼
院务塔（南端，前导）  两侧：药草温室庭 / 器材店
        │ 主轴（南→北，沿坡上行）
星泉广场（主轴与东西横轴交点，泉水居中）
   西：藏书馆（二级地标）    东：长桌食堂（二级地标）
        │
星穹主院（COURTYARD + faceInward：礼堂居北，双教学翼楼东西围合）
        │
礼堂（一级地标，主峰，台地最高）     东肩：观星台（二级地标）
外围：西北书院课堂（DENSE 网格）、东侧宿舍街坊（DENSE 网格）、西南试种田与苗圃（CONTIGUOUS）
```

要点：只有一条主轴；广场四边全是重要建筑；生活与教学紧贴广场两侧；台地自北向南 72 → 68 → 64 逐级下降；农林和码头在外围低处。

### 对照示范：同一座学院按人定区

下面只示范估算顺序，数字为说明用；实际以本城职责和 templateFacilityCapacities 为准。

```text
【工作】教学区   教师 8、院务 2；服务学生 60 座 → 礼堂 1 + 课堂 3（每栋在岗按约 4 人估）
【工作】研究区   研究员 8 → 实验楼 2（虽然每栋有 35 个工位，在岗仍按约 4 人估）
【工作】文献区   文献员 3 → 藏书馆 1
【工作】生活服务 餐食 6、洗衣 2、医护 2、用品 2 → 食堂 2、洗衣房 1、医务 1、商店 1
          岗位合计 33；不上班的学生 60 → 全城人口 93
```

## 流程与阶段成果

| 阶段 | 目标 | 本阶段需要形成的成果 |
| --- | --- | --- |
| 理解要求与场地 | 把城市职责转成空间需求 | 需要哪些活动；入口、制高点、主轴方向；哪些条件尚不确定 |
| 全城构思（OVERVIEW） | 定骨架、主次与人口 | 城市意图（写明主轴、中心、一级地标及其位置，以及按人定区估出的岗位、人口、床位和公共容量）、按主次排列且标明大类的 districts、全城设置 |
| 逐区设计（DISTRICTS） | 把各区挂到骨架上 | 建筑与阵列、嵌套、公共空间和景观、本区 population，以及初次编译结果 |
| 全城复核与修订（INTEGRATION） | 从实际图像修补整体性与人气 | 找出孤立组团、断开的轴线、尺度失衡的空地；核对各区人口之和与床位、岗位、公共容量，以及公共区是否在通勤路上；定向修订并再编译 |
| 最终保存 | 证明四项目标均已落实 | 当前预览的具体 assessment、功能保留确认与定稿 |

当前 d4Workflow.instruction 说明本阶段操作。程序自动推进只代表已保存一份有效初版；城市设计是否充分，仍需在全城复核时判断。

## 信息与工具如何使用

先读 citySeed、scaleDesignTask、D3 总览和 siteReviewDecision，再按本区用途查素材。materialCatalog 提供摘要；city_d4_materials 查询分类、原始用途、风格与尺寸，city_d4_example 查询布局案例及 public_realm 公共空间目录，city_d4_blocks 查询实际方块。具体工具参数以本次 schema 和 submissionRules 为准。无需为了设计读取整份存档或编译几何。

素材的特色/通用类别、基建/景观标签、用途和风格相互独立。本次核心、必需配套、可选填充由设计决定。作者的原始用途与风格是依据，未实现的传送、供能等玩法不得从名称推断。

## 字段与程序边界

- 阵列算法：GRID、LINEAR、COURTYARD、CENTER_SYMMETRIC、COMPACT、ORGANIC_COMPACT、CONTIGUOUS。先明确空间目的再选算法。
- 根建筑组或根组合用 anchorBlock 明确世界方块坐标；嵌套成员由父布局组织，省略独立坐标。按 D3 地图判断位置，程序负责具体成员落位和编译反馈。
- 一个功能区声明一个核心，相关组共享该区台地归属。核心代表功能和高程归属，几何中心由设计决定。
- 道路通过明确 CONNECTION 服务真实目的地。public_realm 提供可组合的庭院、广场模板和池。
- D4 预览用于检查平面组织、边界、碰撞与实际保留内容；支撑、台地和跨水等适配仍需后续施工。将计划内容、预览保留内容和施工结果分清。

## 看图修订与停止依据

正常生成先完成各区有效初版，再实际读取当前 baseDraftHash 对应的局部与全城预览。修订优先级：整体性问题（孤立组团、根锚点过散、轴线断开、广场空洞）高于数量问题。避免为了细枝末节反复重画。用户明确要求测试或修订时，可复用同一 D3 多轮比较。输入错误按反馈修正，程序故障与失败预算遵循宿主状态。

完成判断须回答四项目标，指出具体区域和可见关系。比较计划与实际保留内容：哪些必需内容仍成立，哪些缺口影响功能。当整体已经成立、各项职责都有承载空间时，就可以停止扩展；"还有空地"本身不是扩展理由，保留的自然空间也是构图的一部分。
