## 已确认问题

### C1 · Codex · P2：入口楼梯不核对末端道路高度，制造新断口

位置：[CityEntranceAccessPlanner.java:24](https://github.com/RinsingEL/StructureBinder/blob/2e10af9c/src/main/java/com/rinsing/geomantia/systems/city/application/landuse/CityEntranceAccessPlanner.java#L24)，主要生成逻辑在第 34 行。

入口地坪 Y72，门外原路从 Y68 逐格升至 Y72 时，算法只记第一格的高度，随后把四格改成朝门方向的 Y72、71、70、69 楼梯，却保留紧接着的 Y72 路面。楼梯尾与道路相差 3 格，NPC 仍不能连续通过；报告却为 `connectedEntrances=1`、`warnings=[]`。应同时约束入口和坡道末端，并检查两侧既有路面的连续性，不能只按第一格高差决定楼梯长度。

验证：`CodexGroundProbe.entrance()`，完整输出见 `runtime/campus-branch-review/codex-CodexGroundProbe.log`。这是算法复现，未声称已在实际学院坐标复现。

### C2 · Codex · P2：人口数字缺省通过 D4，进入居民配置后空指针

位置：[CityPopulationBudget.java:12](https://github.com/RinsingEL/StructureBinder/blob/2e10af9c/src/main/java/com/rinsing/geomantia/systems/city/domain/blueprint/CityPopulationBudget.java#L12)，第 18 行同类问题；下游 `QuickCityPlan.expand` 第 34、39 行。

`residents` 和岗位 `count` 校验时允许缺省为 0，但返回的 JSON 没有补入默认值。`QuickCityPlan` 和人口 review 随后直接 `get(...).getAsInt()`。分别省略居民人数、岗位人数的合法预算均通过构造校验，随后在快速配置中抛 `NullPointerException`。应统一必填策略或在边界上写回默认值，并覆盖 D4 → Realmfolk 的交接测试。

验证：`RealmReviewProbe` 两种输入均复现，日志 `codex-RealmReviewProbe.log`。

### D1 · DeepSeek · P1：整个连通路网共用一个方向，T 形道路产生 3 格断差

位置：[CityTerraceRoadGradePlanner.java:94](https://github.com/RinsingEL/StructureBinder/blob/62ed7d2e/src/main/java/com/rinsing/geomantia/systems/city/application/landuse/CityTerraceRoadGradePlanner.java#L94)，方向选择第 107 行，定坡后再次改高第 64 行。

算法按连通组件的总包围盒判断 X/Z 方向。十字路、T 形路、转弯接通后属于同一组件，支路会套用错误的横断面。含入口固定点的整行又被跳过，最后一次 `unify` 没有重新满足相邻高差约束。在同一 T 形路输入上，DeepSeek 出现 32 条横向不等高边、最大相邻落差 3；Codex 为 0 条、最大落差 1。应按真实路段建立断面并在求解阶段统一约束。

验证：`CoreReviewProbe.roads()`，两分支对照日志。

### D2 · DeepSeek · P1：默认无墙城市失去出城道路

位置：[CityWallReservationPlanner.java:71](https://github.com/RinsingEL/StructureBinder/blob/62ed7d2e/src/main/java/com/rinsing/geomantia/systems/city/application/CityWallReservationPlanner.java#L71)。下游 `CityExitRoadPlanner` 仍依赖闭合 `wallLine` 判断城内点与出口候选。

town/village 默认返回无墙空计划，没有保留供交通规划使用的城市轮廓。正式 D5 随后调用的出城道路规划因没有候选而对所有城际连接返回 `NO_SAFE_CITY_EXIT`。同一矩形城区、既有内部道路和城际目标，Codex 生成两段路及一个 portal，DeepSeek 生成 0 段路并报告未解决连接。物理城墙开关不应删除交通规划所需的城区边界。

验证：`CoreReviewProbe.noWallExit()`。无墙计划仍保留 D3 bounds 不能解决该问题。

### D3 · DeepSeek · P2：显式全城/分区材质仍被村路覆盖

位置：[CityVillageRoadPlanner.java:38](https://github.com/RinsingEL/StructureBinder/blob/62ed7d2e/src/main/java/com/rinsing/geomantia/systems/city/application/landuse/CityVillageRoadPlanner.java#L38)。

只检查 `selections.roads()` 是否按道路类型配置，没有检查 defaults/groups 的有效选择。在 village 设置 `defaults.roadSurface=minecraft:stone_brick_slab`，输出仍是 `minecraft:dirt_path`。town 规模跳过村路使学院样例通过，但“小聚落显式材质优先”仍未修好。Codex 相同输入保留石砖。

验证：`CoreReviewProbe.village()`。

### D4 · DeepSeek · P2：D5 城市域除草掩码在正式激活时被丢弃

位置：[CityReservationMaskPlanner.java:72](https://github.com/RinsingEL/StructureBinder/blob/62ed7d2e/src/main/java/com/rinsing/geomantia/systems/city/application/CityReservationMaskPlanner.java#L72)，下游 `CityPlanningEndpointHandler.maskPlanWithLockedEnvelopes`。

新掩码类型为 `city_domain_no_vegetation`，但 execute_d5 重建锁定掩码时只保留 `wall_reservation` 并重建建筑掩码，城市域那条被移除。D5 预览里看到 52 条不能证明实际激活保留整城除草域。用一个城市域掩码调用真正的激活转换，条数从 1 变成 0。应在激活交接中保留它并验证持久化重载。

验证：`CoreReviewProbe.domainMask()`；这是 DeepSeek 新增掩码与既有转换器之间的集成缺陷，Codex 不采用该掩码方案。

### D5 · DeepSeek · P2：人口字段仅写入 codec/验收报告，正式作者入口和居民消费者没有接通

位置：[CityBlueprintCompilerService.java:884](https://github.com/RinsingEL/StructureBinder/blob/62ed7d2e/src/main/java/com/rinsing/geomantia/systems/city/application/CityBlueprintCompilerService.java#L884)。

`CityD4Workflow.validateBody` 第 420 行的白名单没有 population，mergeChanges/assemble 也没有对应交接；正式逐区设计提交人口预算会直接报未知字段。即使绕过该入口直接给完整蓝图写 population，数据仅留在 compilationAcceptance，`CityWorksheet`/`QuickCityPlan` 不读取它，无法兑现“按分区人口展开快速配置”。需要同时接通正式入口、冻结产物和 Realmfolk 消费者。

验证：反射调用正式 validateBody 复现拒绝；对新增字段在相关代码中进行引用追踪。Codex 对应入口接受预算并传给快速配置。

### D6 · DeepSeek · P2：容量目录从错误根目录查找，正式配置看不到床位

位置：[CityPlanningExtension.java:140](https://github.com/RinsingEL/StructureBinder/blob/62ed7d2e/addons/realmfolk/src/main/java/com/rinsing/realmfolk/server/CityPlanningExtension.java#L140)。

`PlanningExtensionContext.runDirectory` 是包含 city_seed_registry 与 city_test_runs 的运行产物目录，不是游戏根目录。新增逻辑却在该目录下找 planning_source/config；实际设施运行时使用 FMLPaths.CONFIGDIR 与 geomantia.providerPlanningSourceDir。因此正常目录布局下返回 EMPTY，新增展示与提交容量校验被静默跳过。应复用实际设施目录/冻结快照，不能猜测游戏根。

验证：构造正式目录层级，目录直接加载 `known=true`，从正式 runDirectory 调用新增方法得到 `known=false`，日志 `deepseek-RealmReviewProbe.log`。

### D7 · DeepSeek · P2：活动半径迁移覆盖作者新写的有效设置

位置：[Design.java:117](https://github.com/RinsingEL/StructureBinder/blob/62ed7d2e/addons/realmfolk/src/main/java/com/rinsing/realmfolk/design/Design.java#L117)。

每次 resolve 都把所有 <=128 的半径改成 384，无法区分旧默认和作者刻意选择。新配置的 16～128 格虽能通过验证，实际永远不生效，近邻活动会被扩展为跨城通勤。明确配置 64，解析后为 384；Codex 保持 64。迁移应有版本/来源依据，显式配置必须可保留。

验证：`RealmReviewProbe`，两分支同输入对照。
