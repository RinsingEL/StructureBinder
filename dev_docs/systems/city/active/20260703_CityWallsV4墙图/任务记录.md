# City Walls v4 墙图开发记录

## 背景

本轮针对真实游玩预览中暴露的城墙问题开发 `wallVersion=v4`：

- v3/v3.3 墙线容易被 source patch 锁死，无法稳定包住 D7 `actualFootprint`。
- 连续湖 / 海水体边上会出现普通墙落水。
- 长段墙在执行层再切分，重复执行与高差场景容易出现墙片叠墙或连接不顺。
- 烽火台 / 门楼 / 墙体之间缺少明确 connector，高低差下步道衔接不舒服。

## 本轮实现

- D5 reservation：
  - 新增 `wallVersion=v4`。
  - D5 仍复用 v3 reservation mask / corridor 上下文，标记 `finalBoundaryDeferredToD7=true`。
  - 最终边界不在 D5 source patch 上定死，交给 D7 ledger 后的 v4 wall graph。

- D7 城墙规划：
  - 新增 `city_wall_plan.v0.4`。
  - `wallBoundaryMode=actual_footprint_land_ring`。
  - 输出 `wallNodes[]`、`wallUnits[]`、`nodeConnectorUnits[]`、`cityWallDatumY`、`wallGraphValidation`。
  - `wallUnitLengthBlocks=16`，普通墙以短 unit 为执行单位。
  - 使用全局 datum + 局部 median + clamp 的高度基准：每个 node / unit 写 `surfaceMedianY`、`targetY`、`heightMode`。
  - 连续水体 run 达阈值后尝试陆侧退避；角点残留水体会二次退避，失败才转 `natural_boundary_gap`。
  - 高差 `3..6` 生成 `stepped_wall_unit` / `stair_link`，高差 `>6` 插入 `terrace_node` 并写 validation break。

- 执行层：
  - v4 按 `wallNodes[]`、`wallUnits[]`、`nodeConnectorUnits[]` 执行。
  - `nodeConnectorUnits[]` 在 report 中输出 `connectorStatus` / `connectorMode`。
  - 地形采样忽略本系统已放置的石砖墙、塔、门楼木梁 / 木板和楼梯材料，降低重复执行叠高风险。

- 预览：
  - v4 预览按 graph 分层绘制：wall unit、stair connector、terrace node、gatehouse、natural boundary endpoint。

- Workflow / MCP / HTTP：
  - MCP schema 增加 `wallVersion=v4` 和 v4 参数。
  - `city_run_workflow skipExisting=true` 在城墙阶段校验已有 plan 的 `wallVersion` / `wallDesignPolicy` / `wallTerrainPolicy`，避免 v3 plan 误跳过 v4 重算。

## 实机反馈修复：节点和墙体双轨

现象：

- 游戏中能看到 v4 节点和墙体明显偏移，节点像一圈独立柱子，外侧另有一圈闭合墙。
- 本次版本不容易看到门楼。

定位：

- `wallUnits[].blockBounds` 在水体退避后使用了最终墙带坐标。
- `wallNodes[]` 和 `nodeConnectorUnits[]` 仍使用 `V4UnitDraft.startX/startZ`，这是退避前的原始 ring 中心线坐标。
- `v4NodeType()` 对普通中间节点也返回 `beacon_tower`，执行层因此每 16 格独立放一个节点柱 / 烽火台。
- 结果是 graph 语义上“节点连接墙体”，但实际放置上形成“内侧节点柱列 + 外侧墙带”两套几何。

修复：

- `CityWallPlanner` 改为从最终 `V4UnitDraft.bounds` 推导节点 / connector 坐标和 bounds。
- 普通中间节点降级为 `junction`，写 `placementRole=graph_only`。
- `gatehouse` 节点 bounds 直接覆盖触发道路开口的 skipped wall unit，保证门楼落在墙线开口上。
- `CityWallPlacementBackend` 对 `junction` / `beacon_tower` 不再独立放置实体节点，只由相邻 `wallUnits[]` / `nodeConnectorUnits[]` 表达连接；保留 gatehouse / corner_tower / terrace_node 的实体节点语义。
- 新增测试：
  - `wallPlannerV4AlignsNodesWithWallUnitsInsteadOfCreatingInnerColumnRing`
  - `wallPlannerV4PlacesGatehouseNodeOnSkippedRoadUnit`

## 实机反馈修复：右上角断开 / 墙线跑出扫描域 / road mask 误开门

现象：

- 预览图右上角断开，且部分墙线看起来跑到未扫描 patch 外。
- 修正水体退避边界后，曾出现 98 个 `wallUnits[]` 全部变成 `natural_boundary_gap` 的退化预览。
- 再次修复水体精度后，右上角和北侧仍大量红色 gatehouse opening，门楼 / 墙段被过度打断。

分层定位：

- L2 求解层：水体退避候选没有限制在 D5/D3 已知 patch 域内，也没有排除与相邻 unit 重叠，导致右上角墙线可被退避到 `knownPatchBounds` 外；这不是单纯预览渲染问题。
- L1 数据精度：D5 `seedPatches[]` 只保留 patch envelope，真实 D3 中一个 `water` patch 的 envelope 覆盖 512x512 扫描域；v4 读取该 envelope 后把整圈误判为水体。
- L3/L2 road mask：`CityRoadMaskScanner` 把 `stone_bricks` / `cobblestone` / `andesite` 等城墙或结构材料当作 road-like，复跑时旧墙材料进入 `actualRoadMask`，v4 又把大量 unit 标为 `ROAD_MASK_GATEHOUSE_OPENING`。

修复：

- `CityWallPlanner`：
  - 增加 `knownPatchBounds` 输出和水体退避候选校验，要求退避后仍在已知 patch 域内且不与其他 unit 重叠。
  - v4 水体 patch 优先使用 `memberCells[] + cellStepBlocks` 展开为 16x16 水体 cell；只在缺少 cell 时回退 envelope。
  - `shore` 不再直接作为 v4 普通墙禁止落点。
  - v4 road bounds 过滤明确的 masonry false positive blockId，兼容旧 `actual_road_mask.json`。
- `CityWallReservationPlanner`：
  - D5 `seedPatches[]` 保留 `geometryMode`、`cellStepBlocks` 和 `memberCells[]`。
- `CityPlanningEndpointHandler`：
  - 对旧 D5 artifact 做内存级 D3 cell 补全，不需要手动重跑 D5 即可让 `plan_city_walls` 使用 D3 精细 cell。
- `CityRoadMaskScanner`：
  - road-like 材料收窄为 `dirt_path` / `gravel` / `coarse_dirt` / `packed_mud` / `mud_bricks`，不再把石砖、圆石、安山岩视作道路。

## 修复：D3 只刷新中心 GIS region 导致 patch coverage 不足

现象：

- 新区块压力测试 `city_realm_salt_kingdom_0_port_703_-720` 的 v4 预览右侧墙线超出 patch 背景。
- 数据确认：

  - D3 patch memberCells union 只到 `maxX=90111`。
  - v4 `knownPatchBounds.maxX=90115`。
  - v4 `wallBounds.maxX=90127`。
  - `outsideKnownPatchUnitCount=23`。

分层定位：

- `L4 展示层`：预览没有漏画；patch backdrop 只画 D3 `landformPatches[].memberCells`。
- `L2 求解层 / D3 patch 真值`：`GisRefreshService.refresh()` 只刷新 `regionForBlock(center)` 单个 AtlasRegion。该测试点中心 region 为 `x=89600..90111`，所以即便 CitySiteContext grid 写到 `90496`，D3 patch 也只覆盖中心 region。
- 结论：问题不是简单 `radiusChunks + 2` 不够，而是 City D3 没有按 city bounds 覆盖多个 GIS region。

修复：

- `CityPlanningEndpointHandler.handlePlanD3`：
  - 新增 `patchScanPaddingBlocks`，默认 128。
  - D3 按 `city grid blockBounds + padding` 计算 `patchContextBounds`。
  - 覆盖 `patchContextBounds` 触达的所有 GIS region，并逐 region 调用 GIS refresh。
  - 将多 region patches / memberCells 合并成同一个 D3 review package。
  - D3 package 写入 `patchScanPaddingBlocks`、`patchContextBounds`、`refreshedRegions[]`。
- `CityLandformReviewBuilder`：
  - 新增 `buildFromRegions(context, regions, patchContextBounds)`。
  - `grid` 仍保持城市核心规划域；padding 只扩大 patch/memberCells 上下文，不把外圈变成 D4 可选核心域。
- `city_plan_d3` / `city_run_workflow` MCP schema 增加 `patchScanPaddingBlocks`。
- `CityWallPlanner`：
  - `wallGraphValidation` 增加 `actualFootprintInsideKnownPatch`、`wallBoundsInsideKnownPatch`、`outsideKnownPatchUnitCount`、`outsideKnownPatchUnits[]`，后续可直接从 JSON 判断是否需要补扫 / 重跑 D3。
