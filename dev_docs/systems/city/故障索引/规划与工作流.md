*修复*：删除 COMPACT 的正弦长轴与左右无限外推，改为每圈八方向径向候选；同一圈全部方向耗尽后才进入外圈。首栋提交后把布局核心重定位到真实首栋，后续建筑围绕已形成建筑核心继续生长。巷道连接改为从已连接节点选择可达的最近新节点；局部无路时保留结构化视觉失败，不再直接抛异常中止编译。

# CITY-PW-20260827-03 LINEAR 精确槽位重复求值与失败预览膨胀

状态：已修复，自动与真实三区复验通过。

*现象*：真实三区商业区局部图显示约 245 个密集失败标记，看起来在空旷区域生成大量“脸贴脸”候选；本轮 D4 trace 达 63,991,603 bytes，实际调用约 40 秒。

*首次偏离*：`CityBlueprintCompilerService` 已为 LINEAR 精确槽位生成固定 `candidateOrigins[]` 后，仍把包含全部连续生长 Patch 的 `candidatePatchRefs[]` 交给 `CityStructureArrayCandidatePlanner`；planner 随后逐 Patch 调用 `buildGroup()`。

*根因*：`exactCandidateOriginsOnly=true` 时，`rawPoints()` 只返回固定 origins，pivot Patch 不参与坐标生成，但外层仍遍历 519 个 source Patch，导致相同的 5 个微调点重复执行 519 次。不同 fill template 又从槽 0 重扫相同 LINEAR 条带。商业区 82 次 selection 中有 75 次 `skipped_illegal_slot`、3 次 `no_legal_candidate`；共写出 122,096 条失败位置记录，实际只有 85 个唯一世界坐标。渲染器按 `templateId + 坐标 + reasonCode` 去重，仍会把同一世界位置的模板/原因变体分别绘制，因此约 245 个红叉并不代表同等数量的独立落点。

*修复*：`exactCandidateOriginsOnly=true` 时，每种 pattern 只选择包含首个 origin 的一个 pivot 并执行一次有序求值；理论点失败后才继续微调点，首个合法结果立即结束，不再产出按 Patch 复制的候选组。LINEAR 记录真实已提交槽位前沿；不同 fill 模板从当前前沿开始，最多检查前沿附近两个槽位，不再从槽 0 扫到远端。预览按世界坐标聚合模板与原因变体，一个位置只绘制一个 X，并在摘要保留合并原因和出现次数。

*验证*：新增精确 origins 回归证明首点被占用时才落到第二个微调点，两个 source Patch 仍只生成 1 个候选和 1 份 generation report；新增预览回归证明同坐标不同模板/原因只形成一个标记。候选器、编译器、布局器和预览器聚焦回归通过；全量 Java 测试通过。真实同案重编耗时 33.844 秒，`compilationAcceptance.passed=true`、质量 100；商业区仍提交 4 栋，但 selection 从 82 降至 10、raw failure records 从 122096 降至 18、唯一失败坐标从 85 降至 6、trace 从 63,991,603 bytes 降至 348,954 bytes。
