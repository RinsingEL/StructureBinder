# 周期性主线程卡顿诊断

*需求入口*：用户报告生物停止、攻击与破坏草延迟，以及全开放后地图仍反复提示更新；要求先提交已有地图修复后继续检查。

*初始诊断阶段*：当时只诊断，未修改产品代码、存档或安装包。对测试端 Java PID42288 采集两次线程快照及30秒JFR profile，核对源码和存档文件变化。

*验证结果*：sample1 的 Server thread 位于 CityWorldgenBlockObservationRegistry.buildObservation → flushPending → onServerTick，逐方块构造JSON并同步追加文件；每tick限制2条但未限制单条方块数量或耗时。观测目录统计1306文件、959.1MiB。sample2 的 Server thread 位于 PlanningAreaAccessPolicy.sourceStamp → PlanningAreaAccessRuntime.refreshIfNeeded → policySnapshot，执行Files.walk与文件属性查询。实际realm_debug有6932文件，只有26文件命中权限来源筛选；100tick周期在服务器线程执行。采样前后9份队列/城市生成报告更新（包含仅mtime变化），导致权限快照失效并通过GeographicAreaAccess.load重建完整GeographicRegions。30秒JFR提取1311个主线程执行/原生样本，673个包含GeographicRegions；部分栈截断，比例是采样观察而非精确墙钟归因。日志曾报告111178ms落后，不能将该整段停顿全部归因于本次采样。

地图screen每100tick无条件refresh，将loading设true；渲染已有图时只要loading就显示更新。地图worker也调用sourceStamp，完成响应需回服务器线程发送，因此主线程卡顿还会延长提示。全开放并不会停用这套轮询。上一轮只缓存地图解析与视口，未覆盖共享权限runtime的同步重建或城市观测主线程写盘。

证据：run/map_diagnostics/threads/sample1.txt、sample2.txt、stall-check.jfr、stall-samples.json、stamp-baseline.json。性能记录已自动结束。

*实际修复*：PlanningAreaAccessRuntime 的周期指纹读取和权限快照重建使用单独 daemon worker，每个 server 最多一个待处理刷新；首次载入/显式失效仍同步建立有效权限。旧异步任务不覆盖显式失效后的新状态。权限语义未变时保留现有 ticket/boundary 缓存。sourceStamp 改为读取已知目录和权限来源，保留新增、删除、fallback 报告、会话、蓝图与激活文件变化。地理分区按文件版本及近海/海域参数缓存；激活结果按存档、维度、两个激活文件及蓝图版本缓存，仅保留一个最近快照。Cell 坐标哈希改为混合64位坐标，避免矩形网格集中碰撞。

City 方块状态仍在生命周期回调读取，完整 JSON 构造和追加写盘由独立单线程执行；每次只调度一个 drain，失败不移除队首，可重试；正常停服等待写入，失败保留待写证据并报错。地图100tick自动检查静默，首载、手动刷新、视口变化仍显示加载反馈。
