# 冒险家地图 Provider 交互故障

*需求入口*：用户在 Forge 47.4.23 真实存档验收冒险家地图，反馈 W 扫描始终未开始、模型厂家与自动规划选择会自动恢复、保存并测试没有可见反馈。

*修改内容*：Provider 设置页增加本地 dirty / save-pending 状态；轮询仍刷新后台自动化信息，但编辑或保存期间不再用旧快照覆盖表单，只有明确保存完成响应才重新同步配置。保存服务在异步落盘前先发布 `saving`，测试请求先切换 `testing` 再回送快照，避免旧状态插队。清除 Key 按钮移到 Key 输入框同行，保存/测试与自动化反馈移到操作按钮上方。启用自动规划保存成功后立即唤醒 runner，不再额外等待轮询周期。实机继续发现 Agent 在 T2 只冻结 Patch Explorer selection、未提交正式 `realm_t2_select_coordinate` 时，普通文本结束会被误认成阶段完成；runner 现于每轮返回后重新读取 discovery，只有进入非 actionable 状态或 semantic identity 变化才承认推进。相同 actionable identity 以 30 秒间隔重试，连续 3 次无推进后以 `PROVIDER_AGENT_NO_PROGRESS` 停止，需显式 `retryNow` 解锁。

*过程可见性*：冒险家地图和 Provider 设置页新增“Agent 过程”窗口。服务端保留最近 160 条安全摘要，每秒按独立网络请求刷新；展示阶段/国度/城市、模型公开消息与 reasoning summary、工具名和少量身份参数、结果状态、正式推进及重试计数。完整 JSON、图片 Base64、任意非白名单参数与凭据不进入事件流；长文本统一截断。该窗口只提供可见决策摘要，不暴露 Provider 不返回的内部推理。

*W 范围权威*：实机过程窗口证明 Provider 把 W 半径自行缩为 1024，而首个国度核心硬门禁要求距原点至少 3072，导致整个候选全集数学上不可能通过 T2。正式 W 现固定以 `config/geomantia/world_survey.json` 为唯一范围来源，默认半径 8192、中心固定原点；HTTP/MCP/Provider/Forge 命令均不能覆盖范围，Provider tool schema 删除范围字段。配置半径小于首城最小距离时扫描前直接失败。Provider discovery 只恢复与当前世界种子、原点中心及配置半径一致的 run，自动 runId 加 `_r<radius>` 后缀；现有 1024 run 保留为历史证据但不会继续消费。

*T4 Provider 交接*：8192 实机运行进入 T4 后，Agent 连续创建会话但首都提交报 `PROVIDER_AGENT_TOOL_FAILED`。最早失败点是 Provider 网关仍按旧根级 `realm_t4_patch_planning_<id>.json` 查找会话，而正式 T4 已使用 `realm_t4_patch_planning_<id>/planning_session.json`；现已与正式落盘契约对齐。实机调用还把展示候选 `VALLEY-01` 直接传为 `patchSelectionRef`，网关现明确要求 `psel_...`，返回 `PATCH_SELECTION_REF_REQUIRED`，工具描述同步强调必须先调用 `patch_explorer_select_candidate` 冻结候选。

*D4 Provider 契约*：实机进入 `city_submit_d4_blueprint` 后，Agent 因 Provider schema 只公开 Blueprint 根字段、内部对象均为空 schema，而按校验错误逐项猜测 `designIntent` 等必填字段。现将正式 codec 的嵌套结构直接公开到工具 schema，覆盖 artifact ref、design intent、profile ref、group、阵列、关系、连接参数、户外空间与景观填充；模板和 profile 仍必须使用 context catalog 中的正式 ref。

*Agent 失败收敛与 D4 回包*：Provider 请求失败不再清空连续未推进计数；相同 semantic identity 的请求失败和成功但无产物统一计入 3 次边界，过程窗口显示 `1/3`、`2/3`，第 3 次停止并等待显式重试。D4 workflow 不再只保留泛化 reasonCode，会从完整 compile trace 中提取紧凑 `failureSummary`：失败 group、structure ref、phase、candidate 数、过滤原因、hard blocks 与建议动作；不向 Agent 复制巨大原始 trace。状态查询还会在宿主侧为旧版已落盘 job 从现有 trace 即时补齐摘要，不重编 D4、不消耗失败预算。本次实机样本可直接显示 `civic_core / plains_fountain_01 / INTERNAL_FRONTAGE_UNAVAILABLE / D4_ARRAY_LAYOUT_FRONTAGE_ENTRANCE_AMBIGUOUS`。

*验证结果*：截图中厂家和启用状态的 1～2 秒恢复与 40 tick 刷新周期一致；运行环境 `provider.json` 在操作期间实际创建并更新，但内容仍为默认 DeepSeek、`enabled=false`。首次修复实机运行后，W 16/16 tiles 与 16384/16384 micro cells 完成，T1 生成 3 国；T2 于 `realm_0` 选中 `PLAIN-01`，但缺失 `realm_coordinate_selections.json`，01:16:35 后无新产物，准确复现假排队。推进验收修复后 Provider 定向测试与客户端代码编译通过。T4 修复新增真实目录会话转发与候选 ID 拒绝回归；`ProviderPlanningToolGatewayTest`、`DeepSeekToolLoopClientTest` 聚焦测试通过。D4 schema 快修按用户要求未运行测试，`reobfJar` 编译打包通过。本轮新增 `PlayerProviderAgentRunnerTest` 覆盖 Provider 请求失败 `1/3`至 `3/3` 停止，`CityWorkflowStepRunnerTest` 覆盖喷泉入口歧义的紧凑回包；与 `DeepSeekToolLoopClientTest`、`ProviderPlanningToolGatewayTest` 合跑通过。

*剩余问题*：需重新打包并重启客户端，实机确认 T4 从既有 open session 先冻结 `psel_...`，再成功登记首都并继续城市规划。
