# 实机规划边界故障诊断

*需求入口*：用户测试新包后报告 CPU 高占用、随后自行恢复；继续报告 T3 截图错误 `PLANNING_HOST_BLOCKED: No assignable land cells for normalizationGroup: primary_realms`。本轮仅诊断与留档，未获本轮明确修复请求，不改运行数据或实现。

*修改内容*：仅登记以下两个已确认缺陷；未停止进程、触发 MCP、调用模型、重试规划或修改存档。

## T3 分组与大陆身份混用

*现象*：新档 `RTF_beta_validation_02` 的 run `provider_ce6a3c351fa2667b_r8192` 完成 W/T1/T2 后，在 14:33:05 进入 T3 即被阻塞。

*首次偏离*：T1 schema 把 `scalePlan.normalizationGroup` 作为任意非空字符串接收，未校验它与地理范围的关系；T3 消费时隐含要求该字符串等于大陆 ID。

*根因*：实际三国目标大陆分别为 `continent_0/continent_11/continent_1`，分组均为 `primary_realms`。`w_manifest.json` 确认这三个大陆存在，面积分别为 4379/3863/1319 cells。`buildTerritory` 同时用 group 过滤 profile 的 normalizationGroup 与 cell 的 continentId，逻辑分组不是大陆 ID，故陆地集合为空。此外 `expandT3` 省略分组时只选首个 profile 的分组，不符合接口承诺的“全部已选目标大陆统一扩张”；仅改 profile 的分组名不能解决多大陆调度遗漏。

*修复*：尚未修复。应明确逻辑分组和地理范围的职责，由目标大陆/宿主规则确定可分配范围；实现多大陆完整扩张与原子发布，补 T1→T3 集成用例。不能把所有国家临时挪到同一大陆来隐藏错误。

*验证*：只读代码、截图与实际 artifact 交叉确认。W manifest、feature grid、profiles、三份选择与 realm seeds 文件仍存在；当前没有 T3 report 或 territory map，具备保留前置结果继续验证的材料，但尚未实际验证修复后续跑。

## 退出世界后 W 并行采样未取消

*现象*：同一客户端先前旧 run `provider_9e2743330c496617_r8192` 在世界退出后继续微采样。14:13:28 HTTP/世界服务停止、14:13:30 保存完成，14:16 仍打印进度和进度文件写入失败；约 3 秒进程采样显示 Java PID 628 占总 CPU 75.1%。14:17:16 微采样达到 16384/16384 后任务失败结束，随后相同进程 CPU 降为 0.7%。

*首次偏离与根因*：世界停止只对 API executor 调用 shutdownNow；`WorldSurveyRunner.buildFeatureGrid` 使用 parallel stream，采样路径没有共享取消令牌或生命周期检查，API 线程中断没有取消并行工作。未开 RTF 影响耗时，但不是退出后继续运行的原因。

*修复与验证*：尚未修复；日志和代码确认，未另启动高负载复现。用户看到的“突然好了”是任务最终耗尽，不代表取消缺陷消失。需补退出时取消和有限时间内停止采样的回归。
