# Provider 超时无限重试

*需求入口*：真实运行约一小时仍未生成首城；用户反馈运行端看不到有效日志且等待过久。

*现场证据*：`provider_6df596ea43fe4b3_r8192` 首城从 20:15:19 至 20:38:42 共九次调用 `prepare_d4_blueprint_context`，间隔约 189 秒，始终没有 `city_submit_d4_blueprint`。线程栈证明 `Geomantia-Provider-Agent` 阻塞于 `DeepSeekToolLoopClient.requestChatCompletions -> HttpClient.send`；当前 Provider 为 `glm-5.3-flash / chat_completions / timeoutSeconds=120`。首轮约 10 秒完成工具选择，第二轮携带 D4 Context 后超时。正式 Context 为 2,931,517 bytes，其中 D3 的 545 个 `landformPatches` 占主体，`memberCells` 单项合计约 802 KB（紧凑 JSON）。

*根因*：一是 D4 Context 原样回灌 Provider，包含 AI 设计不需要逐格读取的完整 Patch 几何，导致第二轮消息过大；二是准备同一 Context 会刷新 queue `updatedAt` 和文件时间，而 discovery 把这两项纳入 `semanticIdentity`，每次请求失败都被误认为新身份，三次失败停机计数因此不断清零。

*修复*：正式 D4 Context 与磁盘证据保持不变，仅在游戏内 Provider 传输层投影为已复核 interest types 的 Patch 摘要并去掉逐格几何、邻接全集和重复 facts；Agent 可见投影明确记录原始/交付 Patch 数和省略字段。真实样本从 545 个 Patch / 1,491,773 个紧凑字符降至 104 个 Patch / 198,367 个字符，减少 86.7%。语义身份改为阶段、scope、nextAction、稳定状态码与正式上游 artifact stamp，不再使用操作性时间戳或 queue 文件时间。Agent Activity 增加每轮请求大小、超时和耗时。

*验证结果*：Provider discovery、失败计数和 tool loop 三组定向测试通过；全量 713 项测试通过，0 failure / error；JAR 构建成功，SHA-256 为 `011B030614D57CBFC8B1CEFA75EE55816441FEBC52F613A1D8533F2DFA9781C6`。

*部署*：已在游戏关闭后部署到测试实例；目标哈希与构建产物一致。被替换包备份为 `mods/geomantia-0.1.0.pre-20260904-provider-timeout.jar.bak`，SHA-256 为 `D306AA56DFE808EFD581BA06275A22240F366EBD172D46248BA1F6178EBCA4DF`。

*剩余问题*：重启后确认第二轮 Provider 请求能在 120 秒内返回并产生 `city_submit_d4_blueprint`；若 Provider 仍连续失败，稳定身份会在 3 次后明确停止，不再无限消耗时间。

*首次实机复验补充*：新日志显示第二轮仍发送约 2781 KiB 并在 120 秒触发 `HttpTimeoutException`。运行时同时确认 Minecraft 通过本机 `127.0.0.1:7890` 代理出站，但消息体大小已足以解释主要延迟。进一步核对发现真实工具响应把 Context 包在根级 `cityBlueprintContext` 中，首版传输投影只匹配了根级 `d3ReviewPackage`，因此实际未压缩；已将投影入口修正为兼容真实 wrapper，并把测试 fixture 改为真实响应形状。修正后针对性与全量 713 项测试通过，重新部署 JAR SHA-256 为 `222CB429666633A24F8F1E957C0233BD35EA1504CC644AED114B0E40F873EF42`；被替换包备份为 `mods/geomantia-0.1.0.pre-20260904-nested-context-projection.jar.bak`。
