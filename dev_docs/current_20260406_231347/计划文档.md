# Vanilla Child 失败机制拆解计划

## 本次任务标题

为独立 `city_jigsaw_solve` 增加 runtime 真值驱动的 vanilla child 失败机制拆解，并增强第 04 步预览图。

## 最终计划摘要

本轮围绕 `/city_jigsaw_solve` 的 `no_valid_jigsaw_solution` 做机制级诊断增强，不改 `start` 选点、`start_connector_dir` 和 C7/C8 seed 逻辑。求解器将在保留当前 vanilla 调用结果判定的前提下，新增一套只读手工兼容分析器，基于 runtime 模板枚举 child jigsaw 候选，解释是卡在 `target/name`、`attach`、`bounds/area`、`terrain` 还是 `vanilla_empty_stub`。同时增强第 04 步调试 trace 与预览图，保证从响应、trace.json、runtime 日志和 png 都能直接看懂失败机制。

## 实施步骤

1. 在 `CityVanillaJigsawAdapterService` 中新增 runtime child jigsaw 手工兼容分析，产出结构化候选和汇总结论。
2. 扩展 `SolveResult.debug` 与 `/city_jigsaw_solve` 第 04 步 evidence，写出 `manual_child_connector_candidates`、`manual_attach_summary`、`first_blocker_stage`、`vanilla_stub_generated` 等字段。
3. 增强 `CityJigsawSolverPreviewExporter` 的第 04 步预览，画出 parent connector、startPos、child 候选矩形和颜色区分后的失败阶段。
4. 补充定向测试，覆盖 `no_valid_jigsaw_solution` 场景下的诊断字段、中文结论和预览产物。
5. 同步更新实现仓库 `dev_docs` 与文档仓库 `02_jigsaw_solver.md`、验收文档，说明新的 debug 输出契约。

## 验收标准

- `no_valid_jigsaw_solution` 时，第 04 步 trace 中能看到 `manual_child_connector_candidates`、`manual_attach_summary`、`first_blocker_stage`、`vanilla_stub_generated`。
- 诊断基于 runtime 模板真值，不依赖 catalog 才能解释 child attach 失败。
- 第 04 步 png 能画出 parent connector、startPos 和 child 候选矩形，并能用颜色区分主要失败类型。
- `jigsaw_north_7_1_0` 与 `jigsaw_up_6_1_8` 两类 runtime connector 场景都能得到明确的机制级中文结论。
- 文档仓库同步更新调试输出契约与验收重点。

## 关键假设

- 本轮不改 `start` 朝向和 seed 选点策略，只聚焦于把 vanilla child 失败机制看清楚。
- 当前加载到运行时的 mod / test lib 结构模板才是诊断真值；若与 catalog 漂移，runtime 优先。
- `JigsawPlacement.addPieces(...)` 的返回仍是最终求解成败依据，手工分析只用于解释失败，不改变现有求解行为。
