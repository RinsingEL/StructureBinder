## 最终结果

第一轮结果：城市队列与 W/D3 在线执行主链可运行，且当前系统不会在没有 Provider 的情况下自动跑到底；它停在唯一当前城市的 `waiting_for_agent`，完成 D3 后仍需 Agent/Provider 准备并提交 D4。越序城市被正确拒绝。

未完成项：

- 固定 acceptance 的 T4 质量有 1 个城市种子越出 owned territory，本轮完整质量验收不通过；这不等于队列机制失败。
- `realm_w_refresh` 真扫 4096 半径为约 65 秒，超过 MCP 客户端默认 60 秒，调用者需要更长 timeout 或异步任务状态入口。
- W 与 D3 都因 `generator_context_unavailable` 退回 Minecraft prior，未覆盖 RTF native fast path。
- 初始区内/区外 TP 与已开放城市 TP 需要客户端手动输入正式命令复验；本轮只确认配置生效和第一城距离符合下限。
- D4 后自动编译到 `waiting_for_generation` 需要一份真实 Provider/Agent 提交的有效 Blueprint；本轮没有伪造 AI 输出，因此没有越过该边界。

### 推进阻断分层诊断

- `run/config` 中没有 `d4CandidateMode`。自动 Post-D4 任务报 `D4_WORKFLOW_MODE_REMOVED`，而不携带该请求字段的手动 `city_run_workflow` 能进入 D4 编译，说明旧字段来自后台续跑请求构造/契约漂移，不是玩家队列配置。
- 公开 City 契约仍写 `city_run_workflow` 默认 `d4CandidateMode=blueprint`，实际入口已拒绝该字段；文档与运行时接口不一致。
- 托管 `template_catalog.json` 仍为根字段 `schemaVersion=city_template_catalog.v0.1`，托管 `blueprint_reference_catalog.json` 为 `city_blueprint_reference_catalog.v0.8`；当前请求采用无版本 wire `schema`。这属于真实配置格式陈旧，但本 run 已通过 `runtime_inputs/city_template_catalog.json` 和近期成功 Reference Catalog 快照完成 Context，因此不是当前 Post-D4 阻断。
- 已接受蓝图有 3 个 Group、`relations=[]`；提交校验 `valid=true`，D4 编译也形成 18 anchors，但终审以三个 `FUNCTION_AREA_RELATION_UNSPECIFIED` 判硬失败，`structureGraphConnected=false`。同时 courtyard 仅形成 0.8 基础环，记录 `COURTYARD_BASE_RING_INCOMPLETE`。这是 Blueprint 校验、公开“无显式连接可合法为空”契约与编译终审之间的第二处不一致。
- 当前城的 Blueprint 已消耗唯一正式提交次数。`city_post_d4_auto_compile_retry` 只允许在修复程序失败后复用同一 Blueprint，不能补写关系；因此不改变契约/实现时，本 run 无法合法推进到下一城。
