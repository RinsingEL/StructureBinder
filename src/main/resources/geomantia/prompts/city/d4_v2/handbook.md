# D4 城市设计流程

## 设计目标

把本城要求落实为适应现场地形、功能完整、具有整体性且规模充分的城市。每次进入世界都应能探索一座有文明生活的异世界城市；依据这次地形和作者素材作出具体设计。

设计与终审始终检查四件事：

1. **满足城市要求**：citySeed 的定位、coreFunctions、gameplayRequirements 与服务地位，落实到实际建筑、配套和公共空间。说明这些空间服务谁、发生什么活动。
2. **地形与功能相互关联**：入口、中心、安静区域、生产和生活等安排利用真实地貌与群系；说明为何放在那里、如何与其他空间联系。
3. **全城成为整体**：核心、各区、公共空间与过渡空间形成可辨识的空间组织。隔河、广场和绿带可以分隔，也可以联系；以实际预览判断。
4. **规模充分**：按城市职责和现场容量设计有深度的组团、配套与重复功能建筑。根据功能需求和现场容量决定体量与是否扩展；不设建筑或阵列数量指标。少量建筑已能编译，不足以证明城市完成。

## 流程与阶段成果

| 阶段 | 目标 | 本阶段需要形成的成果 |
| --- | --- | --- |
| 理解要求与场地 | 把城市职责转成空间需求 | 需要哪些活动、利用哪些地形、哪些条件尚不确定 |
| 全城构思（OVERVIEW） | 组织功能区、主次关系与预期规模 | 城市意图、按主次排列的 districts、全城设置与空间组织理由 |
| 逐区设计（DISTRICTS） | 每区形成核心与完整配套 | 建筑与阵列、嵌套、公共空间和景观，以及初次编译结果 |
| 全城复核与修订（INTEGRATION） | 从实际图像补足功能、联系与规模 | 找出薄弱区域，定向修订并再编译，依据新图继续判断 |
| 最终保存 | 证明四项目标均已充分落实 | 当前预览的具体 assessment、功能保留确认与定稿 |

当前 d4Workflow.instruction 说明本阶段操作。程序自动推进只代表已保存一份有效初版；城市设计是否充分，仍需在全城复核时判断。

## 信息与工具如何使用

先读 citySeed、scaleDesignTask、D3 总览和 siteReviewDecision，再按本区用途查素材。materialCatalog 提供摘要；city_d4_materials 查询分类、原始用途、风格与尺寸，city_d4_example 查询布局案例及 public_realm 公共空间目录，city_d4_blocks 查询实际方块。具体工具参数以本次 schema 和 submissionRules 为准。无需为了设计读取整份存档或编译几何。

素材的特色/通用类别、基建/景观标签、用途和风格相互独立。本次核心、必需配套、可选填充由设计决定。作者的原始用途与风格是依据，未实现的传送、供能等玩法不得从名称推断。

## 空间表达规则

- 先明确阵列的空间目的，再选择 GRID、LINEAR、COURTYARD、CENTER_SYMMETRIC、COMPACT、ORGANIC_COMPACT 或 CONTIGUOUS。使用有用途的重复建筑和小配套形成体量与层次。
- 根建筑组或根组合用 anchorBlock 明确世界方块坐标；嵌套成员由父布局组织，省略独立坐标。按 D3 地图判断位置，程序负责具体成员落位和编译反馈。
- 一个功能区声明一个核心，相关组共享该区台地归属。核心代表功能和高程归属，几何中心由设计决定。不同子阵列应服务不同空间用途。
- 道路通过明确 CONNECTION 服务真实目的地。庭院、广场、花园和绿化应有服务对象、入口与过渡关系；public_realm 提供可组合的模板和池。
- D4 预览用于检查平面组织、边界、碰撞与实际保留内容；支撑、台地和跨水等适配仍需后续施工。将计划内容、预览保留内容和施工结果分清。

## 看图修订与停止依据

正常生成先完成各区有效初版，再实际读取当前 baseDraftHash 对应的局部与全城预览。发现影响城市要求、整体性或规模的明确问题时，作必要的定向修订并看新版本结果，避免为了细枝末节反复重画。用户明确要求测试或修订时，可复用同一 D3 多轮比较。输入错误按反馈修正，程序故障与失败预算遵循宿主状态。

完成判断须回答四项目标，指出具体区域和可见关系。比较计划与实际保留内容：哪些必需内容仍成立，哪些缺口影响功能，哪里还值得扩展。决定停止扩展时，给出功能已充分、合理容量限制、应保留的自然空间或其他现场依据；数量统计和无报错只是辅助证据。
