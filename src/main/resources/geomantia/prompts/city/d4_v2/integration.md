# 阶段三：复核全城，修订并扩展

## 目标

通过当前实际全城图和必要局部图，检查手册的五项目标；把薄弱部分改到足以承担这座城市的职责与地位。

## 复核顺序

1. **功能是否展开**：按 citySeed 的主要功能与玩家活动，逐个片区说出它展开成了哪些子区、各有什么活动与空间。只有一个核心加几栋配套的“大标签区”，就是还没展开；补成相邻的子区，而不是只加几栋楼。
2. **场地是否用好**：对照总览列出的主要用地，逐片说明它现在承担什么；没有去向、或保留理由只有一句“保留林地”的用地，要么规划，要么写出具体理由。
3. **地形是否参与设计**：位置与朝向、岸边和高差、安静与热闹区域、保留的自然空间是否有清楚的用途依据？计划中依赖的地形适配是否仍待施工？
4. **是否是一座整体城市**：在全城图上依次检查：能否一眼读出主轴和中心？一级地标是否唯一且位于轴线尽端或高点？是否有远离骨架、只靠长路连接的孤立组团？根锚点是否过多、过散？广场是否比围合它的建筑大得多而显得空洞？庭院四周的楼是否朝向庭院？是否所有组团都用同样的间距和密度？隔河和合理留白可以成立，说明图上的依据。整体性指连续，不限制城市大小。
5. **城市生活是否成立**：按时段想一遍：白天工作区、饭点和傍晚公共区、夜里居住区，是否都有足够的空间与人？居住与公共是否宽裕？公共区是否落在居住与工作之间的通勤路上？各区 population 相加只用来核对床位、岗位与公共容量是否大致可信，不为对上数字压缩城市。
6. **体量是否与地位相称**：比较本城服务地位、功能需求、场地和图中实际体量。首都或全国唯一的城市应是国度里最重要的地方。新增内容沿骨架与相邻子区生长，不在远处另开孤立组团。

## 修订操作与规则

编译结果里的 CITY_REVIEW_* 告警指出整体性和人口问题（根组团过多、间距或密度全同、同一素材重复过多、内院超尺度、缺人口预算等）。逐条判断：能改的就修订，确实合理的在 assessment 里写明理由，不要直接忽略。子区多、根组合随之增多本身不是问题，问题是组团之间不相接。

把发现的问题落实到具体功能区，用 city_d4_district 指定 targetDistrictId，提交新的完整 districtDesign、designAnswers、当前 baseDraftHash 与 assessment。其他区设计和布局保留。city_d4_mark 和 city_d4_integrate 是可选空间组织能力，其用途和允许修改范围以 schema、submissionRules 为准。

正常生成优先修订功能未展开、用地无去向、生活不足和整体断裂的问题；修改后重新编译并看新图，避免无目标的循环。功能需要时大胆配置阵列和配套。“不报错、不出界、全部保留”只说明程序可行，不是完成的理由。用户明确要求测试或修订时，可复用同一 D3 多轮比较。工具给出 finalize 作为 nextAction，表示允许提交，完成判断仍由上述复核决定。

## 最终保存依据

assessment 基于当前图，分别说明五项目标：每个片区展开成哪些子区，每片主要用地的去向，主轴、中心、一级地标的位置与可见关系，城市生活是否成立，规模为何与地位相称。先解决影响职责成立的必需内容缺口；可选填充和适配告警结合用途判断。若当前证据不足，调用 city_d4_preview 补充图像。

满足这些依据后，用 city_d4_finalize 提交当前 baseDraftHash、assessment、functionsPreserved=true。想保留后续修改机会时明确 autoAdvanceAfterD4=false；默认会推进后续施工准备。无法改善或遇到宿主阻塞时，如实报告当前结果与剩余问题。
